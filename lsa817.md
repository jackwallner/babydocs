# Baby Docs target-user release audit

Audit date: 2026-08-17  
Product: Baby Docs: Newborn Paperwork  
Decision: NO-GO for public release

## Executive decision

The app has a strong product shape and a better-than-average understanding of the
newborn paperwork problem. The local-only architecture, free core plan, source
footnotes, and hard-versus-suggested deadline distinction are all defensible.
The visual hierarchy is also much closer to a usable one-handed tool than to a
generic checklist.

It is not ready to ship because the current build can:

- put the last actionable control behind the floating tab bar;
- show a guessed follow-up date as if an office gave it to the parent;
- schedule a hard reminder for a plan-specific FSA window that the app does not
  know;
- show a federal Marketplace date as a hard date to families using a state
  marketplace;
- create a financial task whose eligibility is broader than the current IRS
  rules;
- ship a newborn-screening rule whose cited page is explicitly marked unread;
- silently lose a local edit when SwiftData save fails;
- merge document completion across different children;
- create an incomplete second-child record when the edit sheet is dismissed;
- force a parent to guess at legally and financially meaningful answers;
- attach App Store build 9 while the repository and current binary are build 10.

The first four are direct trust failures for the app's central promise. The
multi-child issues are release blockers for any Plus customer. The accessibility
failures affect the people most likely to need larger text. These are not
polish items.

## Scope and method

This is a target-user audit, not a code review alone. I inspected the current
source, exercised the built app, and checked the current first-party source pages
behind the load-bearing rules.

- Dark mode at accessibility-extra-extra-extra-large text.
- Screens inspected: welcome, intake, plan, task detail, children, child
  detail, documents, settings, share menu, paywall, and optional intake pages.

Verification:

- The test run emitted 140 compiler warnings, primarily Swift 6 main-actor

  the editable App Store version has build 9 attached while build 10 is the

Current first-party source checks:

- The [Department of Labor childbirth special-enrollment page](https://webapps.dol.gov/elaws/ebsa/health/72.asp)
  confirms a 30-day request window for employer group coverage and birth-date
  effective coverage.
- [HealthCare.gov special enrollment guidance](https://www.healthcare.gov/coverage-outside-open-enrollment/special-enrollment-period/)
  confirms a baby-related Marketplace window of up to 60 days, while the app

- [IRS Publication 503](https://www.irs.gov/publications/p503) explains dependent

  guidance says the written employer plan controls the elections.
- The current [IRS Trump Accounts page](https://www.irs.gov/trumpaccounts) and

- The [HRSA newborn-screening results page](https://newbornscreening.hrsa.gov/newborn-screening-process/newborn-screening-results-and-follow)
  is a real, relevant page, but SourceManifest.swift still marks it as
  awaitingReview.

## Target users considered

### 1. Exhausted first-time parent with an employer plan

This is the primary persona. They have one hand free, are working from a
hospital room or nursery, and are likely to trust a red card more than a
paragraph of caveat text.

The current first-run experience is understandable at the standard size. The
plan leads with the job-based enrollment task, gives the date, shows the
documents, and keeps the official link free. That is the right product moment.

The failure modes are serious:

- the hard card and bottom navigation compete for the same vertical space;
- the FSA toggle can create a third hard reminder even though Settings says
  only two dates are real doors;
- turning on Sent it immediately creates an unconfirmed date;
- the app asks the user to answer several optional questions before it has shown
  the plan;
- the welcome screen says nothing entered leaves the phone, although the app
  later offers deliberate sharing.

### 2. Marketplace family using HealthCare.gov

The federal 60-day rule is represented and the source is appropriate. The
family still needs to know that a first premium is required and the app includes
that document item.

The issue is that the app presents the 60-day date as a hard fact before it has
established whether the family is using the federal Marketplace or a state
marketplace. A caveat in the detail text does not make a notification generated
from the federal date safe.

### 3. Family using a state Marketplace, Medicaid, CHIP, or no coverage

These families need routing more than a generic list. The app gives a federal
Medicaid or CHIP link and a general statement that state eligibility controls.
That is honest, but it leaves a parent with a newborn and no coverage still
searching for the actual agency.

The no-coverage path is also not the same as a Medicaid or CHIP path. It is
reasonable to show Medicaid or CHIP, but the app should explain that the answer
is a prompt to check eligibility, not an assertion that the family qualifies.
There is no hospital financial-assistance or charity-care task for a family
whose hospital bill is not covered by an employer or Marketplace plan.

### 4. Unmarried parents, parents with a contested relationship, or a parent
who does not want to disclose the relationship

The app has a meaningful parentage rule and its legal caution is good. The
intake still forces the user to select married, unmarried with both parents
involved, or single parent. ParentageSituation.unknown exists and is labelled
Prefer not to say in the model, but OnboardingFlow filters it out.

This is both a privacy failure and a plan-integrity failure. A parent who does
not want to answer may choose a false value, and a false value changes whether
the legally significant task appears.

### 5. Immigrant, mixed-status, or noncitizen household

The citizenship toggle is present, and the app avoids asking for an SSN. That is
good. The default is still US citizen, and the user gets no neutral or not-sure
state. The newborn-account path also conflates the $1,000 pilot contribution
with the broader question of whether an initial Trump Account can be opened.

The app supports only the states, DC, and Puerto Rico in USState.all. It does
not support Guam, American Samoa, the Northern Mariana Islands, or the US
Virgin Islands. It also has no country or overseas-military path.

### 6. The second parent receiving a plan link

The free share link is one of the strongest parts of the product. It carries
answers in the URL fragment, does not carry completions or vault images, and
makes the independent-copy behavior explicit.

The import screen's action label is not safe enough when a recipient already
has children. It says Add this child to my plan, while the implementation
replaces household answers and rebuilds every child's plan. That is a much
larger effect than the label suggests.

The seed also contains the child's name, while the privacy and plan-page copy
describes the payload as a birth date, state, county, and household answers.
The documentation should either name the child name explicitly or remove it
from the seed.

### 7. Parent with two children, closely spaced children, or twins

This is the highest-risk Plus persona. The documents list deduplicates by title
across every child and then marks every matching title on every child as
gathered. A parent who ticks one child's proof of birth can therefore complete
the same document on another child's plan.

Adding a second child also creates and saves a child before the editor is
completed. The sheet has no Cancel action, no validation on Done, and can be
dismissed with an empty name, today's date, or an inherited birth state. A
same-day twin cannot be safely matched by birth date and birth state when a
shared plan is imported.

### 8. Parent with low vision, large text, or a small screen

The accessibility text-size test exposed two direct failures:

- the welcome title, explanatory copy, and privacy copy truncate with visible
  ellipses at accessibility-extra-extra-extra-large;
- the Plan card grows into the floating tab bar, and the tab bar covers the
  lower plan content.

The standard text size looked orderly enough to hide this problem. The target
user cannot be assumed to use the standard size.

### 9. Parent using the phone at a counter or while offline

The local plan, document list, and vault are well aligned with this use case.
The app does not need a login, has local reminders, and keeps the core plan
available without a server.

The official links still require a network, and the share link requires a
message or browser path. The app should distinguish what works offline from
what only becomes actionable once the external office is reachable.

### 10. Parent buying Plus

The free-versus-paid boundary is mostly honest and the paywall names the
features that are actually gated. The paywall screenshot shows a real problem:
the fixed purchase bar covers the selected weekly card's trial text on first
presentation. The detailed purchase terms are also set in caption2 with low
contrast and are easy to miss while the user is deciding.

The simulator verifies layout and StoreKit Testing placeholders, not a real
RevenueCat purchase, restore, trial conversion, lapse, or vault-retention
cycle. Those need a device or TestFlight sandbox pass.

## Release blockers

### R-01, P0: Floating tab bar covers actionable content

Observed in the running app:

- On Plan, the tab bar covers the lower part of the visible task list.
- On Task Detail, the Confirmations section and its Record what came back
  control appear under or behind the bar after scrolling.
- On Child Detail, the Send or print this plan footer is clipped by the bar.
- On Documents, the final visible gather row is clipped and more content
  continues behind the bar.
- On Settings, the Turn on deadline reminders control and its footer sit behind
  the bar.
- At accessibility-extra-extra-extra-large text in dark mode, the primary
  deadline card itself grows into the bar.

The implementation uses AppTheme.planPageBackground() with
contentMargins(.bottom, 44, for: .scrollContent), while RootView hides the
system tab-bar background. The actual bar plus safe-area region is taller than
44 points, and the margin is not applied as a reliable safe-area exclusion for
every List and sheet.

Evidence:

- Normal seeded Plan screenshot: the lower newborn-screening card meets the
  floating bar.
- Scrolled task detail screenshot: Confirmations begins under the floating bar.
- Documents and Settings screenshots: last visible controls are visibly clipped.
- Accessibility screenshot: the tab bar sits across the lower portion of the
  enlarged hard-deadline card.

Why it matters: the user cannot reliably complete, record, or even see the
last control on the screen. This is a functional failure in the main flow and
an accessibility failure.

Recommended fix:

- Use one measured safe-area inset that matches the actual floating bar and
  bottom safe-area height, or stop floating the tab bar.
- Apply the inset to every top-level List, ScrollView, task detail, child detail,
  documents page, settings page, and paywall scroll view.
- Keep the visual glass treatment only after the last interactive row has a
  verified clear path above it.

Acceptance test:

- On every root tab, scroll to the last interactive element and assert its
  frame.maxY is less than or equal to the tab bar frame.minY.
- Repeat at standard, accessibility-extra-large, and
  accessibility-extra-extra-extra-large text sizes.
- Include Task Detail, Child Detail, Sources, Add Document, Share Plan, Settings,
  and Paywall, not only the source footnote.

Related code: Shared/Utilities/AppTheme.swift:135-153,
BabyDocs/RootView.swift:24-45.

### R-02, P0: Sent it creates a fake office deadline

When a parent toggles Sent it, TaskDetailView sets expectedByAt to Date() plus
14 days. The following screen labels that value They said by and the planner
can show a countdown or late state from it.

The surrounding copy says the opposite:

- no turnaround time is hardcoded;
- the only trustworthy figure is what the office told the family;
- the parent is asked to record that figure.

A code comment calls 14 days a placeholder for the picker, but the data model
does not distinguish a placeholder from a confirmed office date. A tired parent
can open the detail, toggle Sent it, leave the screen, and later be told a
fictional date has passed.

Recommended fix:

- On Sent it, record Sent on only.
- Leave expectedByAt nil until the parent explicitly enters a date.
- Show Tell us what they said by or No date given, not a DatePicker preloaded
  with a value that looks confirmed.
- Do not mark the task late until an explicit date exists.
- If a suggested picker default is retained, keep it in transient UI state and
  never persist it or use it for reminders, sorting, or late status.

Acceptance test:

- Toggle Sent it, terminate and relaunch, and confirm no expected date exists.
- Confirm the task never becomes late without an explicitly entered date.
- Enter a date, relaunch, and confirm only that explicit date drives the late
  state.

Related code: BabyDocs/Views/TaskDetailView.swift:180-220 and 268-299.

### R-03, P0: Dependent-care FSA is treated as a known hard 30-day deadline

The dependentCareFSA rule creates a hard deadline 30 days after birth. Its own
basis says the number belongs to the employer plan, not the law. The scheduler
still schedules every task whose deadlineKind is hard, so a family with an FSA
gets a hard notification generated from an unknown plan window.

This directly conflicts with the Settings footer, which promises that only the
job-based health plan and Marketplace dates receive notifications.

The current IRS source supports the concern. Publication 503 explains the
benefit, while the written cafeteria plan controls election rules. The app
already admits this limitation in SourceManifest.swift, but the data model
still promotes the date to hard.

Recommended fix:

- Make the FSA task undated until the parent enters the employer plan date.
- Or make the 30-day value a clearly labelled suggestion that cannot schedule
  a notification.
- Add a separate confirmed-date state and a plan-document input.
- Update Settings only if the product intentionally expands hard reminders.

Acceptance test:

- With FSA enabled, a newly reconciled plan has no FSA notification.
- The FSA row cannot say Hard deadline or show a hard-deadline exclamation
  until a plan-specific date is entered.
- Settings and scheduler tests assert exactly the intended reminder set.

Related code: Shared/Rules/RequirementCatalog.swift:424-459,
Shared/Services/DeadlineReminderScheduler.swift:61-92,
BabyDocs/Views/SettingsView.swift:68-72.

### R-04, P0: State Marketplace families can receive the wrong hard date

The Marketplace rule always creates a hard date 60 days after birth and links to
HealthCare.gov. The rule text says some state-run marketplaces differ, but the
app already knows the family's residence state and still does not route the
family or downgrade the date.

The federal HealthCare.gov page supports the federal 60-day path. It does not
make the same hard date safe for every state marketplace. A caveat below a red
deadline does not undo a notification generated from that date.

Recommended fix:

- Ask whether coverage is HealthCare.gov or a state marketplace.
- For a state marketplace, route to a verified state source or show a
  source-controlled federal fallback with no hard reminder until confirmed.
- If the product intentionally supports only the federal Marketplace, say that
  before the user selects the option and do not imply universal coverage.
- Test states with their own exchange rules before marking any specific source
  verified.

Acceptance test:

- State Marketplace and federal Marketplace are separate rule inputs.
- A state Marketplace family never receives a federal-only hard notification
  without an explicit confirmation.
- The task detail shows the exact source scope in the first screenful.

Related code: Shared/Rules/RequirementCatalog.swift:353-387,
Shared/Rules/SourceManifest.swift:140-152.

### R-05, P0: A shipped rule cites an unread source

The newborn screening task is active for every family. Its SourceManifest entry
is status awaitingReview and says nobody has read the HRSA page end to end.
The task still presents the link and an apparently actionable result request.

The app's differentiator is that every rule shows its working and review date.
That makes the status honest, but it does not make an unread medical-adjacent
source release-ready. The HRSA page is relevant and contains important
distinctions between in-range, out-of-range, and borderline results, plus
follow-up instructions. A human should read it, decide exactly what the app is
asserting, and record the limitations.

Recommended fix:

- Read and verify the page and any state-routing behavior.
- Reduce the task to the records-collection claim the app can support.
- Add an explicit medical urgency boundary for abnormal results.
- Do not ship the active task with an awaitingReview source status.

Acceptance test:

- No active rule in the catalog has status awaitingReview.
- SourceIntegrityTests fails if an active task points to an unread source.
- The task's first-screen copy says what to do if the provider reports an
  out-of-range result, without pretending the app interprets it.

Related code: Shared/Rules/SourceManifest.swift:299-314,
Shared/Rules/RequirementCatalog.swift:748-777.

## High-risk correctness and data findings

### R-07, P1: Newborn-account rule is broader than current IRS eligibility

The rule turns on from citizenship, birth year 2025 through 2028, and the
household toggle. It describes the $1,000 contribution as available to eligible
US citizen children, but does not represent:

- a valid SSN issued before the election;
- whether the child has already had an election or pilot contribution
  processed;
- whether the parent making the election anticipates the child will be their
  qualifying child for the tax year;
- the distinction between opening an initial Trump Account and electing the
  $1,000 pilot contribution;
- the required authorized-individual relationship and representations.

The current IRS instructions explicitly distinguish the broader initial-account
eligibility from the pilot contribution requirements. The app's task should not
make a parent infer that citizenship and a date alone are enough.

Recommended fix:

- Change the intake question to ask whether the parent wants to check eligibility
  for the Trump Account and pilot contribution.
- Gate the task on a current, explicit eligibility checklist, or state clearly
  that the task is only a prompt to read Form 4547.
- Include the no-prior-election condition and the qualifying-child condition in
  the detail.
- Update the source review whenever the IRS changes the online process.
- Consider separate tasks for initial-account election and pilot contribution.

Acceptance test:

- Test a US citizen child without an SSN, with an SSN, with a prior election,
  and for a parent who will not claim the child.
- The UI never promises $1,000 solely from the citizenship toggle.

Related code: Shared/Rules/RequirementCatalog.swift:597-640,
BabyDocs/Views/Onboarding/OnboardingFlow.swift:289-301.

### R-08, P1: Parentage and coverage have no honest unknown state

ParentageSituation.unknown and InsuranceKind.unknown exist in the model, but
the onboarding filters both out:

- parentage offers only married, unmarried both parents, or single parent;
- coverage offers employer, Marketplace, Medicaid or CHIP, or no coverage;
- Continue is blocked until a coverage answer is selected.

The resulting plan is only as good as a user's answer. A user who is unsure,
private, in a changing insurance situation, or legally separated from the
other parent is pushed toward an inaccurate value. That can turn off the
parentage task or turn on the wrong deadline.

Recommended fix:

- Offer Prefer not to say or Not sure yet as a real path.
- Generate a neutral task such as Confirm your coverage window with the plan
  administrator rather than silently choosing a category.
- Explain which tasks are unavailable until the answer is known.
- Keep the legal relationship question optional until it is necessary to show a
  rule, and make the privacy consequence clear.
- Make US citizenship an explicit choice or an unknown state rather than a
  default assertion.

Acceptance test:

- A user can finish intake without asserting a legal relationship or coverage
  category they do not know.
- The resulting plan clearly labels what is pending and never schedules a hard
  deadline from an unknown category.

Related code: BabyDocs/Views/Onboarding/OnboardingFlow.swift:23-41,
176-199, 249-269, Shared/Models/BabyModels.swift:81-121.

### R-09, P1: Local save failures are swallowed

LocalRecord.recordLocalChange uses try? context.save(). The single-profile
creation path in RequirementEngine also uses try? context.save(). This covers
task completion, document ticks, assignments, notes, receipts, profile edits,
child edits, and tombstones.

A parent can see a UI change, leave the screen, and assume it is safe. If a
SwiftData save fails, the app gives no error, no retry, and no indication that
the state is not durable. The app is intentionally local-only, so this is not a
secondary cache failure. It is the only copy.

Recommended fix:

- Make save operations return a typed result or throw.
- Surface a plain-language save error with Retry and Keep editing actions.
- Add an app-level unsaved-state or last-save indicator only if necessary.
- Log enough local diagnostics to support a user without logging family
  content.
- Test disk-full, inaccessible-store, and migration-failure behavior.

Acceptance test:

- Inject a failing ModelContext save and confirm the user is told exactly what
  did not persist.
- A failed save never updates the UI in a way that implies durable completion.

Related code: Shared/Models/LocalRecord.swift:31-47,
Shared/Rules/RequirementEngine.swift:307-323.

### R-10, P1: Documents are deduplicated across children by title

DocumentsView.uniqueOutstanding uses lowercased title as its sole identity.
markGathered then marks every outstanding item with that title on every child.
This is reasonable for repeated documents within one child's rule set, but not
for a family with multiple children.

Example: the parent gathers the birth certificate for child A, taps the single
collapsed Birth certificate row, and child B's same-title document items are
also marked on hand. The task detail and Documents tab then stop asking for a
document that may not exist for child B.

Recommended fix:

- Deduplicate by a semantic document key within one child, not by display title
  across the entire household.
- Include child identity in the gather row and in the mutation set.
- Show one row per child when the same title is needed for different children.
- If one physical document can satisfy multiple tasks for the same child, model
  that relationship explicitly.

Acceptance test:

- Two children with identical document titles can be ticked independently.
- Ticking child A never changes child B's DocumentItem rows.
- The gather list identifies the child whenever more than one child is present.

Related code: BabyDocs/Views/DocumentsView.swift:45-112.

### R-11, P1: New-child creation has no cancel or validation boundary

ChildrenView inserts and saves a new Child before opening ChildEditorSheet.
ChildEditorSheet provides Done and Remove this child, but no Cancel. A swipe
dismissal or abandoned edit can leave a saved child with default values:

- today's date;
- an inherited residence state used as birth state;
- an empty name;
- no required validation.

The requirement engine can then materialize a plan from an incomplete child.
The inheritance is a helpful starting value but is not safe as a silent default
for a child born in another state.

Recommended fix:

- Keep a draft child out of SwiftData until Done, or add a true Cancel path that
  deletes the draft.
- Require a birth date and birth state before producing tasks.
- Show a confirmation before dismissing with incomplete values.
- Ask whether the new child was born in the inherited state instead of silently
  assuming it.

Acceptance test:

- Start Add another child, swipe the sheet down, and confirm no child remains.
- Try Done with no birth state and confirm validation blocks plan generation.
- Add a child born in another state and confirm the state and source update.

Related code: BabyDocs/Views/ChildrenView.swift:66-79 and 235-295.

### R-12, P1: Plan import label understates a household-wide replacement

If the recipient has children, the import action says Add this child to my plan.
The implementation replaces household answers and calls reconcileAll, rebuilding
every child's plan. That may be intended for two parents sharing one household,
but the action is unsafe for a recipient with an existing independent child plan
or a different household configuration.

Recommended fix:

- Label the action Replace household answers and add this child, or split import
  into merge and replace flows.
- Show the exact consequences before applying, including every existing child
  whose plan will be rebuilt.
- Require an explicit confirmation for a non-empty store.
- Preserve local work and explain which fields are never imported.

Acceptance test:

- A recipient with two existing children sees the affected child list and
  replacement warning.
- Cancel leaves every existing task and answer untouched.

Related code: BabyDocs/Views/Sharing/SharePlanSheet.swift:126-195.

### R-13, P1: Same-day twin matching is not unique

PlanSeed import matches an existing child by birth date and birth state. Twins
can share both. The first match then receives the imported name and state, while
the second child is not added.

Recommended fix:

- Carry a stable, non-sensitive child seed identifier in the link, or always
  require the recipient to choose which existing child matches.
- If multiple matches exist, block automatic matching and show a choice.
- Include the name only if the privacy copy explicitly documents it.

Acceptance test:

- Import a plan into a store with two same-day, same-state children and confirm
  neither is changed without an explicit selection.

Related code: BabyDocs/Views/Sharing/SharePlanSheet.swift:173-186,
Shared/Services/PlanSeed.swift:23-37.

## Intake and trust findings

### R-14, P1: Defaults can create false-positive work

The intake defaults to:

- US citizen true;
- Someone is taking parental leave true;
- Newborn account true;
- Married to the other parent;
- second parent on record true.

These are not harmless presentation defaults. They alter the generated plan.
A tired parent can accept the defaults by moving through the optional screens
quickly and then see tasks that imply legal, tax, or financial eligibility.

Recommended fix:

- Use explicit neutral defaults for high-stakes answers.
- Make the first plan show an Answers used summary with an Edit answer action.
- Distinguish “we have not decided” from “no”.
- Do not make a $1,000 financial task opt-out by default without a clear
  eligibility checkpoint.

### R-15, P1: “Nothing you enter leaves this phone” is too absolute

The welcome screen says nothing entered leaves the phone. The app later
deliberately shares household answers in a plan link, shares summaries and
employer packets, and sends purchase information to Apple and RevenueCat.
The privacy policy explains those exceptions, but the first-run copy does not.

Settings repeats a similar statement that everything entered is on the phone,
even though a parent can share generated data from inside the app.

Recommended fix:

- Say “Baby Docs keeps your plan and vault on this phone unless you choose to
  share them.”
- State that purchases are handled by Apple and RevenueCat at the first
  relevant purchase surface.
- Name the child's name if it remains in the plan link payload.
- Keep the no-background-upload claim, which is the accurate and valuable one.

Related code: BabyDocs/Views/Onboarding/OnboardingFlow.swift:107-121,
BabyDocs/Views/SettingsView.swift:112-124, Shared/Services/PlanSeed.swift:23-37.

### R-16, P1: Suggested dates look like deadlines in the Plan list

The list pill renders a recommended date as “10 days left”, the same phrase
used for a hard date. The detail screen eventually says Suggested by, but the
Plan screen is where the tired parent triages.

Orange styling and an absence of the exclamation icon help, but the distinction
is still partly visual. A user with color-vision limitations or a user scanning
quickly can treat the suggestion as a legal closing date.

Recommended fix:

- Use explicit copy such as Suggested, 10 days left.
- Keep Hard deadline in the accessible label and visible compact form.
- Add a short list-level explanation the first time a suggestion appears.
- Do not use “left” for dates that are only a prompt unless the adjective is
  present.

Related code: BabyDocs/Views/Components/HubComponents.swift:15-39,
Shared/Rules/TaskPlanner.swift:132-148.

### R-17, P1: Parentage task is not an actionable state-specific route

The parentage task correctly warns that the form, witnessing, and rescission
rules are state law. Its link is an ACF child-support agency directory, not a
state-verified parentage or vital-records form. An unmarried parent at a
hospital or county office can still be sent to the wrong first door.

The product's cautious generic-link policy is sound, but the task needs a more
explicit route:

- what to ask the hospital before discharge;
- what office the generic directory is expected to identify;
- how to proceed when the parentage situation is contested;
- a clear “do not sign until you understand the rescission rule” boundary.

This is especially important because the task concerns custody, inheritance,
benefits, and the birth record.

Related code: Shared/Rules/RequirementCatalog.swift:501-533,

### R-18, P1: State and territory coverage is incomplete

### Accessibility-specific follow-up

The source makes a genuine attempt to support Dynamic Type in TaskRow and
BadgeRow. That does not cover the whole app. The next pass must include:

- Dynamic Type from extra-large through accessibility-extra-extra-extra-large
  on every screen, not only the Plan.
- VoiceOver order and labels for the separate task completion button and
  NavigationLink.
- VoiceOver announcement of hard versus suggested dates.
- Whether SourceFootnote caption2 text is readable and reachable.
- Reduce Motion and contrast settings.
- Keyboard-visible FeedbackSheet and all text fields.
- A smaller iPhone viewport.
- Landscape behavior if portrait-only remains intentional.

The current LayoutUITests test only whether the source footnote eventually
becomes hittable. It does not test the last interactive control on the Plan,
Documents, Settings, Child Detail, or Paywall screens, and it does not run the
layout assertion at a large content size.

## Privacy and data-handling audit

### Strengths

- No account or household-data backend.
- PlanSeed uses a URL fragment rather than a query string.
- The vault holds filenames in SwiftData and image files with complete file
  protection.
- Vault images are excluded from backup and cannot be reached by PlanExporter.
- The app tracks SSN status rather than storing an SSN field.
- The summary and employer packet tests assert that an SSN number is absent.
- Existing vault access survives a Plus lapse, which is the correct trust
  decision.
- The privacy policy honestly names Apple and RevenueCat as purchase processors.

### Risks to fix

1. PlanSeed includes the child's name, while the privacy and plan-page copy
   describes a payload that omits it. Align the implementation and all copy.
2. The in-app welcome and Settings statements are broader than the actual
   deliberate sharing behavior.
3. Free-text notes and receipt values can hold an SSN as ordinary text even
   though the app tells the user not to. Put the warning next to both entry
   points, and consider rejecting obvious SSN-shaped values locally.
4. The receipt menu includes Submitted, Received, and Note, but the footer says
   confirmation and tracking numbers only. The input title Number or reference
   encourages users to put sensitive material there.
5. Vault deletion removes image files immediately with no undo or confirmation.
   A tired parent can swipe away a Social Security card photograph. Keep
   immediate file deletion after an explicit confirmation, and make the loss
   irreversible warning clear.
6. The share link is readable by anyone who receives or forwards it. That is
   stated in Terms but not strongly enough in the in-app share sheet.

## Pricing, purchase, and release operations

### Pricing presentation

The free boundary is strategically sound:

- every deadline, link, document list, reminder, and one-child plan is free;
- sending the independent plan link is free;
- Plus covers the vault after twelve weeks, further children, printable
  summary, and employer packet;
- existing vault images remain readable after lapse.

The paywall needs layout and disclosure work before release:

- the fixed buy bar obscures the selected weekly trial copy on first view;
- the lifetime option is below the first viewport;
- the terms block is caption2 and low contrast;
- the CTA changes to Start my free trial, but the selected plan's complete
  price and renewal sentence are not always visible in the same first view;
- simulator restore is intentionally unavailable, so it cannot validate a
  buyer's real restore path.

Required manual sandbox pass:

- weekly trial start, cancellation, renewal, and lapse;
- yearly purchase;
- lifetime purchase;
- restore on the same Apple Account;
- restore on reinstall and a new device;
- lapsed subscription with existing vault images;
- attempt to add a new image after lapse;
- purchase failure, network failure, and storefront with no products;
- localized price and period display.

### App Store readiness

The readiness script passed metadata checks, URL reachability, paid-feature
wording, screenshots, age rating, review notes, and product records. It still
reported build attachment drift. That operational gap must be fixed before
submission.

The Store listing also says “Baby Docs asks six screens of questions.” The
current StepDots includes seven question steps: baby, household, coverage,
leave, newborn account, 529, and passport. The listing should either say seven
or describe the optional screens accurately.

## Product scope and cognitive load

The catalog has twenty rules. That breadth is valuable, but the first screenful
can feel like a general life-admin list after the hard insurance item:

- W-4, 529, beneficiaries, guardian, pediatric portal, and childcare waitlist
  are useful but not urgent;
- many recommended dates are prompts rather than externally defined windows;
- the Plan currently groups a 31-day rolling window under “This month,” which
  can include dates in the next calendar month;
- suggested and hard dates share “days left” phrasing.

Recommended product treatment:

- keep the hard deadline card and waiting items at the top;
- label suggestion buckets as “Next 31 days” or use true calendar-month logic;
- make “No deadline” and “Suggested” explicit in the row, not only in detail;
- consider an initial “Now” view with Later and No deadline collapsed until the
  parent asks for the full list;
- keep every rule available, but reduce the cognitive load of the first visit.

## Final assessment

Baby Docs has a credible reason to exist. It is focused, transparent about its
local-only architecture, and its best screens answer the user's real question:
what applies to this family, what has to be brought, and which door closes first.

The current build still asks the user to trust dates and saved work in places
where the implementation does not support that trust. It also fails to keep
the main controls reachable at the text sizes that accessibility users need.
Fix the P0 and P1 items, rerun the full persona and layout matrix, attach the
current build, and only then reconsider release.
